# Swagger MCP：把 API 契约变成 Vibe Coding 的可检索上下文

## 摘要

AI 很会生成接口代码，却不知道你们的接口现在长什么样。开发者如果只给它一句“接入用户详情”，它只能依赖当前上下文补全路径、参数和字段；上下文不完整，生成得越快，错误也复制得越快。

Swagger MCP 的作用，是让 AI 在编码前按需查询 OpenAPI 契约，在编码后回读契约核对结果。它不替代接口设计、契约测试和业务文档，只是把已经存在的 API 契约，变成 Vibe Coding 可以直接检索的上下文。

> 本文以开源项目 [`swagger-reader-mcp`](https://github.com/Abdallahabusnineh/swagger-reader-mcp) 为例。项目能力、工具名和配置以其 GitHub 仓库与 npm 包为准；Claude Code 的配置作用域以[官方 MCP 文档](https://code.claude.com/docs/en/mcp)为准。

## AI 写接口代码，难点不在“写”

接口协作的基础问题并不是 AI 带来的。无论代码由人还是 AI 编写，客户端都需要知道最新的请求路径、参数、响应结构和错误约定。

AI 带来的增量问题，是它只能依据当前可见的上下文工作：

- 没看到契约时，它可能根据命名习惯补出并不存在的字段。
- 拿到旧文档时，它会很流畅地生成一套符合旧版本的代码。
- 一次塞入整份 OpenAPI，会混入大量与当前任务无关的端点和 Schema。
- 生成速度越快，错误类型和调用代码也可能扩散得越快。

**人和 AI 面对的是同一份契约问题，区别在于 AI 会把上下文缺口迅速放大。**

传统流程通常需要多次搬运接口信息：

```text
代码 / Proto / 接口注释
  ↓
生成并发布 OpenAPI
  ↓
复制到 API.md 或知识库
  ↓
客户端查找本次变更
  ↓
再次复制给 AI
  ↓
生成客户端代码
```

每增加一个字段副本，就多一个过期的可能。接口已经更新，知识库可能尚未同步；字段表已经复制，却不一定标明对应版本；AI 最终得到的，未必是当前生效的契约。

## MCP 改变的是 AI 取得契约的方式

接入 Swagger MCP 后，契约不再依赖开发者逐段复制，而是由 AI 在任务执行过程中按需查询：

```text
契约定义源：代码 / Proto / 手写 OpenAPI
  ↓ 生成
发布物：Swagger / OpenAPI JSON
  ↓ 读取与缓存
Swagger Reader MCP
  ↓ 按需查询
AI 编程工具
  ↓ 生成后回读核对
客户端代码
```

这里需要区分三个角色：

- **契约定义源**决定接口如何被维护，可能是 Proto、代码注解，也可能是手写 OpenAPI。
- **OpenAPI 发布物**是客户端和工具可以读取的机器契约。
- **Swagger MCP**是 AI 的统一契约查询入口，而不是新的契约定义源。

以 `swagger-reader-mcp` 为例，它由 AI 客户端通过 `stdio` 启动，读取并在内存中缓存指定的 Swagger/OpenAPI JSON。它提供五个只读工具：

| 工具 | 用途 |
|---|---|
| `search_api` | 搜索路径、操作信息、Schema 和字段 |
| `get_endpoint` | 查询指定路径和 Method 的完整定义 |
| `get_schema` | 查询指定 Schema |
| `get_api_overview` | 查看 API 概览、端点数、Schema 数和缓存信息 |
| `refresh_api_spec` | 跳过缓存，立即重新获取文档 |

这些工具只检查接口文档，不调用文档中描述的业务接口，也不要求后端新增业务 RPC。

## 一个端到端例子：实现用户详情请求

假设当前 OpenAPI 定义了 `GET /users/{id}`，响应 Schema 为 `UserDetail`。开发者不必先把相关 JSON 找出来，可以直接描述任务：

```text
使用 api-docs 查询用户详情接口。
根据实际契约实现请求函数和 TypeScript 类型。
完成后重新读取端点和 Schema，核对路径、参数、必填字段与返回类型。
不要推测文档中不存在的字段。
```

AI 的执行过程应当分成五步：

1. 用 `search_api` 搜索“用户详情”，定位候选端点。
2. 用 `get_endpoint` 确认路径、HTTP Method、路径参数和响应 Schema。
3. 用 `get_schema` 读取 `UserDetail` 的字段、类型和必填关系。
4. 依据查询结果生成请求函数与 TypeScript 类型。
5. 再次读取端点和 Schema，对照生成代码逐项检查。

如果查询到的示例契约是 `id: string`、`name: string`、`avatar_url?: string`，生成代码可以保持在契约范围内：

```ts
export interface UserDetail {
    id: string;
    name: string;
    avatar_url?: string;
}

export function getUserDetail(id: string) {
    return request<UserDetail>(`/users/${id}`);
}
```

这段代码本身并不复杂，关键是每一个字段和路径都能追溯到查询结果。若契约没有 `email`，AI 就不应该因为“用户详情通常有邮箱”而自行添加。

**Vibe Coding 的可靠性，不只取决于模型会不会写，更取决于模型写之前能查到什么。**

## 为什么不直接把整份文档交给 AI

三种方式都能提供接口信息，但适用范围不同：

| 方式 | 优点 | 局限 |
|---|---|---|
| 手工复制相关片段 | 临时使用最快，不需要接入工具 | 容易漏字段、复制旧版本，难以稳定复用 |
| 把整份 OpenAPI 放进上下文 | 一次提供全部定义 | 占用上下文，混入无关端点，大文档还可能被截断 |
| 通过 MCP 按需查询 | 可搜索、可回读、适合重复使用 | 依赖文档可达、检索质量、缓存和 MCP 运行环境 |

如果团队只是偶尔对接一个小接口，手工复制已经足够。只有当接口数量、协作频率或 AI 参与度上升时，把契约接成可检索工具才更有价值。

## 收益、代价与边界

| 维度 | 收益 | 代价与边界 |
|---|---|---|
| 上下文 | AI 按任务取用相关端点和 Schema | 工具调用仍消耗 Token；关键词不匹配时可能漏检 |
| 时效 | 刷新后可读取最新发布物，不必重新复制字段表 | 缓存未过期或未主动刷新时，仍可能读到旧契约 |
| 一致性 | 为客户端和 AI 提供统一的契约视图，减少字段副本 | 前提是定义源、生成物和发布地址之间保持同步 |
| 可验证性 | 可要求 AI 列出依据并在生成后回读核对 | 只能检查代码是否符合文档，不能证明真实接口行为正确 |
| 团队协作 | project 配置可随 `.mcp.json` 共享，并锁定工具版本 | 成员仍需安装 Node、批准配置，并能够访问 npm 与文档地址 |
| 运行环境 | 本地 AI 客户端可以直接启动 stdio 进程 | 仅支持远程 MCP URL 的云端客户端不能直接运行这个本地包 |
| 安全 | MCP 不直接写业务数据，权限边界相对清晰 | 第三方 npm 包仍在本机执行，需防范供应链、敏感文档和地址访问风险 |

这套方案没有消除接口协作成本，而是把问题从“复制得是否正确”，收敛为“发布的契约是否可信、MCP 取得的是否最新”。后者更容易检查和自动化，但仍需要工程治理。

## 文档职责如何划分

接入 MCP 不意味着所有文档都应合并到 OpenAPI。机器契约和业务说明承担的是不同职责：

| 文档载体 | 主要用途 | 适合承载的内容 | 不应重复维护的内容 |
|---|---|---|---|
| Swagger/OpenAPI | 机器可读的接口发布物 | Method、路径、参数、Schema、类型、必填关系、枚举、格式和标准错误响应 | 需求背景、跨接口业务流程和上线决策 |
| 飞书、Confluence 等知识库 | 供团队理解和讨论业务 | 业务目标、页面交互、影响范围、兼容策略、灰度计划和待定决策 | 完整的路径、参数和字段表 |
| 项目内的 `API.md`（可选） | 提供接口使用指引 | 模块概览、复杂调用示例、OpenAPI 难以表达的业务约束和接口索引 | OpenAPI 已描述的字段级契约 |

知识库可以说明为什么改、影响谁、如何升级；具体路径、参数和字段结构则回到 OpenAPI 查询。

## 在 Claude Code 中配置

`swagger-reader-mcp` 通过 `npx` 运行，无需全局安装或 clone 仓库。首次启动时，`npx` 会从 npm registry 解析、下载并执行指定版本的 package；后续通常可以复用本地缓存。

前提是本机安装了 **Node.js 20 或更高版本**，可以先运行 `node -v` 确认。

Claude Code 支持 local、project 和 user 三种 MCP 作用域：

| 作用域 | 适合场景 | 是否随仓库共享 |
|---|---|---|
| local | 个人试用或包含本机专属配置 | 否 |
| project | 团队为当前项目共享同一配置 | 是，写入项目根目录 `.mcp.json` |
| user | 个人跨多个项目使用的通用工具 | 否 |

与项目接口契约绑定的 MCP，通常适合使用 project；试用阶段或配置包含个人地址时，local 更合适。Claude Code 在交互式会话中首次使用项目级 MCP 前会要求批准，团队成员应检查启动命令、package 来源和环境变量。

项目根目录的 `.mcp.json` 可以这样配置：

```json
{
  "mcpServers": {
    "api-docs": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "swagger-reader-mcp@0.1.4"],
      "env": {
        "SWAGGER_URL": "https://api.example.com/openapi.json",
        "SWAGGER_CACHE_TTL_MS": "180000"
      }
    }
  }
}
```

这里锁定 `0.1.4`，是为了避免团队成员在不同时间自动取得不同版本。`SWAGGER_CACHE_TTL_MS=180000` 表示内存缓存默认保留三分钟；接口刚更新但缓存尚未失效时，可以要求 AI 先调用 `refresh_api_spec`。

## 把它纳入工程流程

MCP 只提供查询能力，不会自动保证契约可靠。团队需要明确下面这条链路由谁维护、如何检查：

```text
修改契约定义源
  ↓
生成并校验 OpenAPI
  ↓
发布到稳定地址
  ↓
主动刷新或等待缓存失效
  ↓
AI 查询、生成并回读核对
```

如果发布流程尚未自动调用刷新动作，就应把它称为“待建立的自动化链路”，而不是已经具备的能力。最低限度可以落实以下约定：

- 后端或 API 设计者维护契约定义源，并保证发布物随版本更新。
- CI 检查生成产物差异、格式、关键路由和文档地址可用性。
- 客户端开发者要求 AI 编码前查询、编码后回读，不凭经验补字段。
- 团队锁定 npm 包版本，升级前审查来源、变更和权限。
- OpenAPI 不放真实密钥、生产 Token 或不应进入模型上下文的示例。
- 真实接口行为继续由集成测试或契约测试兜底。

**MCP 让契约更容易被 AI 使用，但契约本身是否可信，仍然是团队的责任。**

## 结论

Swagger MCP 不会替团队设计接口，也不会替测试验证真实行为。它解决的是一个更具体的问题：让 AI 在生成接口代码前，能够找到当前发布的路径、参数和 Schema；生成后，还能回到同一份契约核对结果。

它的价值可以归纳为三点：

1. 少搬运：不再反复复制字段表和整份接口文档。
2. 少猜测：没有出现在契约中的字段，不应进入生成代码。
3. 可回查：路径、Method、参数和 Schema 都能重新查询和人工复核。

契约本来就存在。Swagger MCP 做的，是把一份过去仍需开发者手工查找和搬运的机器契约，变成 AI 能按需查询的工程上下文。对于持续使用 Vibe Coding 进行客户端开发的团队，这个改变很小，却会落在每一次接口对接上。
