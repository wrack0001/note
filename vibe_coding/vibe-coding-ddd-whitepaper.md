# Vibe Coding 新项目的架构选择：模块化单体 DDD 的适用条件与工程价值

> 技术白皮书 · 2026 · v2（重构版）
>
> 姊妹篇：《DDD 的核心优势：为复杂业务系统买的三份保险》（`ddd-core-advantages.md`）——剥离 AI 语境，单讲 DDD 的独立价值与通用落地清单。本文只讲一件事：**对于由多个轻量业务模块组成、以 Vibe Coding 为主要开发方式的新项目，为什么模块化单体 DDD 更适合作为起点。**

---

## 摘要

AI 编程工具（Vibe Coding）大幅提升了代码生成速度，但同时也可能加速技术债的累积。当语义一致性、模块边界与业务不变量主要依赖人工自觉维护时，高频 AI 生成会放大这些软防线失守的风险。

本文讨论的新项目有一个常见特征：用户、资产、IM 消息、直播等模块各自有少量业务规则，不是纯 CRUD，却也没有重到需要独立部署。如果每个模块都拆成服务，会很快增加仓库、契约和发布成本；如果只用三层把它们放在一起，规则归属和跨模块调用又容易依赖人工约定。

本文比较模块化 MVC 三层单体、细粒度多仓微服务 MVC 和模块化单体 DDD，并论证第三种组合为何更适合作为这类新项目的起点：先在一个仓库和部署单元内划清业务模块，让每个模块拥有自己的模型、规则和接口，再根据实际运行需求拆出独立服务。

**核心结论**：对于包含多个轻量业务模块的新项目，先采用轻量的模块化单体 DDD，通常比“一开始拆很多服务”或“规则全部留在应用服务”更平衡。这里的 DDD 不等于上齐聚合、领域事件和 CQRS，而是先落实限界上下文、业务规则入口、Port 和依赖方向；纯 CRUD 可以继续使用三层，确有独立扩缩容或故障隔离需求的模块再拆成服务。

## 1. 问题背景：首次能跑 ≠ 后面改得动

### 1.1 Vibe Coding 的生产力红利

AI 编程工具的普及，让自然语言驱动代码生成成为主流生产方式。功能迭代速度被提升数倍甚至十倍。Vibe Coding 的实践方式并不单一：既包括"几乎不看生成代码、凭感觉连改带跑"，也包括"人定意图、AI 写实现、人审 diff"。本文讨论的是后一种——已经用 AI 主力写代码、却仍要对可维护系统负责的生产场景。

### 1.2 三段式失控曲线

生产实践表明，AI 驱动的开发往往呈现一条三段式时间线：

```
flowchart LR
    T1["第一阶段：首次交付成立<br/>✅ 接口通了，用例过了，演示成立"] --> T2["第二阶段：二次修改失控<br/>⚠️ 一次小改动牵出大面积 diff"]
    T2 --> T3["第三阶段：PR 成为瓶颈<br/>❌ 审不动 / 漏改 / 放过隐患"]
    style T1 fill:#90EE90,color:#000
    style T2 fill:#FFD700,color:#000
    style T3 fill:#FF6B6B,color:#000
```

**第一阶段：首次交付成立。** 对话把需求说清楚，模型把链路写通，业务规则、外部调用、协议拼装可以暂时堆在同一个大 Service 里。功能验证通过，团队容易产生"已经做完了"的错觉。

**第二阶段：二次修改失控。** 需求微调或外部接口变化时，模型缺乏稳定落点，倾向在最近、最大的文件里继续加、继续重写。循环调用、分支判断与字段转换和业务规则缠在一起，一次小改变成大面积 diff。与此同时，先前生成留下的重复实现会把"改一处"变成"改一串"。

**第三阶段：PR 成为瓶颈。** 即便合并前功能仍然正确，人工审查也要在噪声里打捞真正的业务变更，核对多处重复逻辑是否都改到了。审不动，就会要么放过隐患，要么反复打回重生成——两者都在消耗 AI 本该省下的时间。

### 1.3 重复问题的放大效应

AI 写出来的实现里，同一段校验、同一套状态判断、同一种外部调用拼装，经常以轻微变体复制到多处。功能第一次仍然成立，因为每一处"各自能跑"。真正的成本出现在变更时：规则一变，就要同步改很多地方；地方一多，总有改漏——漏掉的那一处往往要到联调、甚至线上路径才暴露。

重复不是"代码丑一点"的审美问题，而是把每一次业务演进都放大成多点齐改，并把漏改变成高概率事件。

### 1.4 根本原因

问题的根源往往不是模型不够聪明，而是沿用了几十年的架构范式，从设计之初就是为"有自觉的人写代码"准备的。当生产主体大量转向大模型，架构的核心使命已经悄然改变：**它不再只是指导人如何实现功能，而是约束生成过程不要突破复杂度底线。**

### 1.5 AI 的第一目标是"让功能能跑"，不是"保护代码结构"

**AI 写代码时，首要目标是解决问题，而不是保护代码结构。**

这不是模型的 bug，是模型的 feature。大模型被训练成"把当前指令完成得最好"：你让它加一个字段，它就把字段加上；你让它改一个逻辑分支，它就改掉。至于这个改动会不会破坏原有的分层结构、会不会让模块边界变模糊、会不会引入重复——这些不是它的优化目标。它的优化目标是：**改完之后，这段代码能跑、能通过当前的测试。**

这就导致一个典型的"按下葫芦起了瓢"的现象：你让 AI 修一个 Bug，它修复了当前路径上的问题，但顺手引入了另一条路径上的新 Bug，或者在修复过程中把之前保持得还算清晰的结构给推倒了。因为在它看来，**代码结构是手段，让功能能跑才是目的**——如果牺牲结构能让它更快地达到目的，它会毫不犹豫地牺牲。

就像盖房子。AI 的首要任务是"把墙砌起来、把屋顶盖上"，至于地基有没有打好、承重墙的位置对不对——等出问题再说。但问题在于，地基没打好的房子，盖到三楼就开始裂缝；盖到五楼可能就塌了。AI 写代码也是同理：前几轮生成看起来一切正常，但随着代码量增加、改动次数增多，结构持续劣化，每一次"能跑"的新改动都在抬高下一次改动的复杂度。Bug 越来越多，每次修复的成本越来越高，直到某次修改彻底失控。

这解释了为什么在 AI 编码的语境下，架构的"约束"价值远大于"指导"价值。传统的架构文档告诉开发者"你应该怎么做"；AI 时代的架构必须告诉模型"你不能怎么做"。前者靠自觉，后者靠结构。**没有结构约束的 AI 编码，就像在地基没打好的土地上盖高楼——不是能不能的问题，是什么时候塌的问题。**

## 2. 三道容易失守的软防线

Vibe Coding 把开发者从编码执行者推向意图表达者与结果验证者。当语义、模块边界和业务规则主要存在于个人经验、口头约定与人工评审中，而没有被编码为可执行约束时，高频生成会放大这些软防线失守的风险。这些问题并非 AI 独有，也不是使用 AI 的必然结果；风险来自上下文不完整、约束不明确，以及生成速度超过验证能力。

```

    subgraph Defenses["传统开发中常见的三道软防线"]

        D1["🛡️ 语义防线"] -->|"⚠️ 容易失守"| B1["同一「用户」多种含义<br/>登录账号 / 客户档案 / 运营人员身份<br/>→ 上下文内术语不一致<br/>跨上下文差异未显式区分"]
        D2["🛡️ 边界防线"] -->|"⚠️ 容易失守"| B2["控制器直连数据库<br/>跨模块修改内部对象<br/>→ 模块耦合上升，改一处牵全身"]
        D3["🛡️ 规则防线"] -->|"⚠️ 容易失守"| B3["已发货订单被直接取消<br/>不允许透支的账户仍被扣款<br/>→ 表面能跑，实则违反业务不变量"]

### 2.1 语义防线：上下文内的概念一致性失控

自然语言天然带有歧义。同一个"用户"，可能指登录账号、客户档案或运营人员身份；团队口中的"订单"，也可能混指销售订单、履约单或退款单。DDD 并不要求这些概念在全系统只有一个含义，而是要求同一限界上下文内部的模型与术语保持一致，并显式区分、映射不同上下文中的含义。

AI 的实现取决于它当时能够获得的上下文，包括提示词、当前文件、关联代码、仓库索引与项目指令。当领域知识没有进入这些可读取的载体时，后续生成容易沿用局部命名，逐渐形成同义不同名、同名不同义，或同一规则出现多种判断口径的问题。

### 2.2 边界防线：模块耦合持续上升

如果模块边界只存在于资深工程师的经验中，就需要依靠评审阻止跨层调用与越界修改。AI 会根据当前任务和可见约束寻找实现路径；当目录、接口和依赖规则没有明确表达边界时，它可能选择控制器直连数据库、跨模块修改另一领域的内部对象，或把业务逻辑散落到工具类与配置中。这些做法能够快速完成局部功能，却会逐步增加模块耦合。

这并非不可避免。目录与包的可见性、公开接口、依赖方向检查和架构测试，都可以让人和 AI 在越界时尽早失败，把原本依赖经验的软边界变成可验证的工程约束。

### 2.3 规则防线：业务不变量被绕过

假设当前业务明确规定"已发货订单不能直接取消""不允许透支的账户余额不足时不能扣款"，这些就是必须持续成立的业务不变量。规则散落在多个入口、领域对象又允许外部直接修改状态时，无论人工还是 AI 生成的代码，都可能绕过原有校验，形成表面通过主流程、实际违反业务规则的实现。高频生成会进一步增加这类遗漏进入代码库的机会。

只验证正常路径的功能测试往往发现不了这些问题；覆盖非法状态转换和边界条件的自动化测试则可以及时拦截。更进一步，聚合入口、类型约束、访问控制和数据库约束可以缩小绕过规则的空间。

**关键不在于 AI 是否"自觉"，而在于约束是否可见、可执行、可验证。DDD 也不会自动形成护栏；只有当统一语言、限界上下文和业务不变量被落实到代码结构、接口与测试中时，软规范才会转化为人和 AI 都必须遵守的工程约束。**

## 3. 两类架构决策与三个常见组合

工程上要分开回答两个问题：**系统如何部署**（一个还是多个仓库、进程和发布单元），以及**代码如何组织**（按技术职责分层，还是按领域语义划分模块）。微服务主要回答前者，MVC 与 DDD 主要回答后者，三者并非互斥。

本章比较三个具体组合：模块化 MVC 三层单体、细粒度多仓微服务 MVC、模块化单体 DDD。

### 3.1 组合 A：模块化 MVC 三层单体

```
flowchart LR
    subgraph M1["用户模块"]
        H1["Handler"] --> S1["应用服务"] --> R1["Repository"]
    end
    subgraph M2["资产模块"]
        H2["Handler"] --> S2["应用服务"] --> R2["Repository"]
    end
    S1 -.跨模块调用.-> S2
```

**定义与成立前提**：一个仓库、一个部署单元，代码先按用户、资产、IM 消息、直播等业务模块组织，每个模块内部再采用 `handler → application service → repository` 三层。一个业务模块可以很大，内部可以包含多个应用服务；它不是一个独立部署的微服务。跨模块协作通过对方公开的模块接口完成。

**Vibe Coding 中的优势**：

- **上手成本低**：业务模块和三层调用方向都很直观，CRUD、后台管理等需求可以快速生成。
- **反馈链路短**：代码位于同一仓库，类型检查、单元测试和构建可以一次完成。
- **具备基本改动局部性**：相关 handler、应用服务和 repository 聚集在同一模块，AI 可以先限定模块再生成；公开模块接口也为跨模块调用提供固定入口。

**Vibe Coding 中的劣势**：

- **跨模块调用容易扩散**：如果应用服务可以直接调用其他模块的内部实现，调用链增长后容易形成循环依赖和跨模块事务。
- **模型归属不够明确**：多个模块可能共享 DTO、数据库模型或状态枚举，调用方逐渐依赖对方内部字段。
- **规则仍可能散落在应用服务**：状态判断和业务规则缺少统一入口时，人和 AI 都可能从不同调用路径绕过约束；AI 还会更快复用已有写法。

**与 DDD 的差别**：模块化三层侧重代码归类和调用入口；DDD 进一步明确模型归属，将业务不变量收口于领域模型，并用公开契约或防腐层隔离跨上下文语义。简单查询与编排使用模块接口即可；出现模型泄漏、规则绕过或术语冲突时，DDD 更有价值。

**适用与不适用场景**：适合模块边界清楚、业务规则能集中在应用服务中维护、跨模块协作简单的系统；当同一规则需要由多个入口共同遵守、状态流转容易被绕过，或模块间语义与依赖持续复杂化时，应考虑引入 DDD。

**本节结论**：模块化三层可以组织大型单体，DDD 也不要求把业务模块继续拆成微服务。当某个业务模块内部积累了复杂状态、业务不变量和语义冲突时，可以在原模块内引入领域模型，深化它的内部实现，而不是新增部署单元。

### 3.2 组合 B：细粒度多仓微服务 MVC

```
flowchart LR
    S1["Service A<br/>用户"] -.-> S2["Service B<br/>资产"]
    S2 -.-> S3["Service C<br/>IM 消息"]
    S3 -.-> S4["Service D<br/>直播"]
```

**定义与成立前提**：系统拆成多个仓库、进程和发布单元，通常一个服务一个仓库，服务内部采用 MVC 三层。开发时可以把所有服务加入同一个多根工作空间，统一检索和修改代码；仓库、版本与发布单元仍彼此独立。

**Vibe Coding 中的优势**：

- **服务级反馈与影响范围可控**：每个服务可以独立构建和测试；数据库权限与网络访问控制还能限制运行时越界。
- **契约可机器读取**：维护良好的 protobuf、OpenAPI、生成客户端和契约测试，可以直接约束跨服务调用。

**Vibe Coding 中的劣势**：

- **服务数量爆炸**：一个小功能一个服务，会同步增加仓库、CI/CD、部署配置、监控、权限和值班对象，长期维护成本转移到系统层面。
- **跨仓修改不是原子变更**：工作空间可以同时编辑多个仓库，但每个仓库仍有独立分支、提交、CI 和合并状态；例如“用户开通主播资格→初始化资产账户→发送 IM 通知→创建直播间”少合并一个调用方或配置仓库，仍会漏改。
- **Proto 演进形成版本链**：通常要依次更新定义、生成并发布代码、升级服务端和各调用方，还要处理兼容性、字段保留和发布顺序。
- **完整验证与发布更困难**：单仓构建通过不代表链路正确；契约测试、集成测试或部署检查缺失，可能让不一致拖到联调甚至上线，并增加漏发和版本错位风险。

人和 AI 面对相同的跨仓协调问题。统一工作空间可以同时查看和修改多个仓库，但各仓库仍需分别提交、评审、合并和发布；任一环节遗漏或顺序错误，都可能造成契约版本不一致、联合验证失败或漏发布。

**适用与不适用场景**：适合服务职责稳定，确有独立扩缩容、故障隔离或团队自治需求，并具备成熟契约和多仓工具链的系统；不适合业务改动经常跨服务、团队却要维护大量小仓的场景。

**本节结论**：细粒度微服务可以提供独立部署、扩缩容和故障隔离，但会把一次业务变更拆成多仓提交、契约演进、联合验证和多服务发布。只有这些运行收益足以覆盖协调与维护成本时，拆分才合理；不能为了缩小单个服务而无限细分。

### 3.3 组合 C：模块化单体 DDD

```
flowchart TD
    I["interfaces<br/>协议 ↔ DTO 转换"] --> A["application<br/>用例编排"]
    A --> D["domain<br/>实体 / 规则 / Port"]
    IF["infra<br/>仓储 / 外部客户端 / 消息消费"] -.实现.-> D
    A -.持有接口.-> D
    D -.- R["🔴 红线：domain 禁止 import<br/>ORM / 协议框架 / 缓存客户端"]
    style I fill:#E3F2FD,color:#000
    style A fill:#FFF9C4,color:#000
    style D fill:#FFCCBC,color:#000
    style IF fill:#C8E6C9,color:#000
    style R fill:#FF6B6B,color:#fff
```

**定义与成立前提**：系统仍放在一个仓库中并整体部署，但代码按用户、资产、IM 消息、直播等限界上下文组织，每个上下文拥有自己的模型和业务规则。上下文内部可以采用四层：interfaces 接收请求并转换数据，application 组织业务流程，domain 保存业务模型与规则，infra 负责数据库和外部系统接入。关键不在目录名称，而在业务规则留在 domain，外部依赖通过 Port 接入。

**Vibe Coding 中的优势**：

- **更容易确定改哪里**：需求先落到对应的限界上下文，相关模型、规则和接口集中在同一模块内，AI 不必在整个仓库中猜测修改位置。
- **业务规则不容易写散**：状态变更和校验放在 domain，数据库、RPC 等代码放在 infra，AI 可以沿着现有结构修改，减少在 handler 或 application 中重复实现规则。
- **错误更容易提前发现**：字段没有同步、Port 没有实现或 domain 引用了外部框架，可以在本地编译、测试或依赖检查时发现，不必等到联调。
- **人工审阅有固定抓手**：同一需求的修改可以在一个 PR 中查看，四层职责又提供固定检查项：domain 是否混入 ORM 或 RPC，infra 是否夹带业务判断，interfaces 是否绕过 application。评审者不必每次从头还原整条调用链，但仍需确认业务规则本身是否正确。

**Vibe Coding 中的劣势**：

- **分了目录也可能越界调用**：代码放进不同模块后，仍可能直接引用其他模块的内部实现。团队需要限制内部代码的可见范围，要求跨模块调用只走公开接口，并用依赖检查拦住违规引用。
- **所有模块仍要一起构建和部署**：系统变大后，完整构建、测试和发布会变慢；某个模块需要更多资源或发生故障时，也不能像独立服务那样单独扩容或隔离。
- **领域模型需要持续维护**：业务术语、模型、规则和 Port 会随需求变化，团队必须及时更新；如果系统只是简单 CRUD，这些维护成本可能超过收益。

**适用与不适用场景**：适合业务规则复杂、跨模块变化频繁，但暂时不需要独立部署的系统；不适合极简单业务，或必须严格隔离故障、独立扩缩容和团队发布节奏的模块。

**本节结论**：模块化单体用语义边界换取改动局部性，但不消除规模与分布式复杂度；未来拆成远程服务时，延迟、重试、幂等和一致性仍可能要求 application 或 domain 调整。

### 3.4 三个组合对比

下表比较的是 3.1～3.3 已定义的三个具体组合。表中结论都以各节的成立前提为准，不代表 MVC、微服务或 DDD 的所有实现都会如此。

| 维度 | A：模块化 MVC 单体 | B：细粒度多仓微服务 | C：模块化单体 DDD |
|------|----------------|----------------------|--------------------|
| 仓库与部署 | 一个仓库、一个部署单元，整体发布 | 多个仓库、进程和部署单元，各服务独立发布 | 一个仓库、一个部署单元，整体发布 |
| 代码组织 | 先按业务模块划分，模块内采用三层 | 先拆成独立服务，服务内采用三层 | 先按限界上下文划分，上下文内采用四层 |
| 模型与规则 | 规则主要放在应用服务；DTO、数据模型可能被多个模块共用 | 规则主要放在各服务的应用服务；跨服务规则可能落在编排流程中 | 每个上下文拥有自己的领域模型，状态变更和校验集中在 domain |
| 模块间协作 | 通过公开模块接口进行本地调用 | 通过 protobuf、OpenAPI、消息等契约进行远程协作 | 通过公开接口或 Port 进行本地调用，必要时转换不同上下文的语义 |
| 一次跨业务改动 | 可以在一个仓库内一起修改和验证；调用关系复杂后容易牵动多个应用服务 | 需要分别修改相关仓库、契约和调用方，并协调合并与发布顺序 | 可以在一个仓库内一起修改；每个上下文只处理自己的模型和规则 |
| 数据库与外部系统 | 可用 Repository 或客户端接口隔离，是否隔离取决于具体实现 | 每个服务分别维护数据库权限、RPC 和消息适配 | domain 通过 Port 表达需要的能力，infra 负责数据库和外部系统接入 |
| 本地验证范围 | 类型检查、单元测试和整体构建可以覆盖同仓代码；规则是否被绕过仍依赖测试 | 单个服务只能验证本仓代码，完整链路还需要契约测试和集成测试 | 类型、测试和依赖检查可发现 Port 未实现、字段漏改和违规依赖 |
| 发布与运行 | 发布简单，但不能按模块独立扩缩容或隔离故障 | 可以独立发布、扩缩容和隔离故障，但要维护版本兼容与发布编排 | 发布简单，但不能按上下文独立扩缩容或隔离故障 |
| 团队协作 | 可以在同一仓库完成评审与合并，模块接口需要共同维护 | 可以按服务划分负责人；跨服务需求需要协调多个仓库或团队 | 可以按限界上下文划分负责人，并在同一仓库完成联合修改与评审 |
| Vibe Coding 的直接收益 | 结构直观、上手快，模块范围明确，反馈链路短 | 服务职责稳定时，单个服务的生成与测试范围较小；契约可以机器读取 | 修改位置、业务规则和外部适配各有落点，错误更容易在本地暴露 |
| 主要风险 | 跨模块调用扩散、共用 DTO 或数据库模型、规则散落或重复 | 服务数量爆炸、跨仓漏改、Proto 版本链和漏发布 | 直接调用其他模块的内部代码、整体构建变慢、业务变化后模型和规则没有及时更新 |
| 审阅重点 | 是否绕过模块接口，规则是否在多个应用服务中重复 | 契约是否兼容，相关仓库是否改全，发布顺序是否正确 | domain 是否守住业务规则，infra 是否只做外部适配，依赖方向是否正确 |
| 成立前提 | 模块接口清楚，应用服务能够集中维护规则 | 服务职责稳定，并具备契约、集成测试和多仓发布工具链 | 团队持续维护业务术语、领域模型、Port 和依赖检查 |
| 适用场景 | 整体以 CRUD 为主，规则可以集中在应用服务中的系统 | 确有独立扩缩容、故障隔离或团队自治需求的系统 | 包含多个轻量业务模块，各模块有自己的术语或少量规则，但暂不需要独立部署的系统 |
| 不适用场景 | 状态流转容易被绕过，模块间语义和依赖持续复杂化 | 业务改动经常跨服务，却拆出了大量小服务的系统 | 简单 CRUD，或必须独立扩缩容、隔离故障和单独发布的模块 |

### 3.5 如何选择：先看运行需求，再看业务规则

架构选择不是在 MVC、微服务和 DDD 之间三选一。先判断模块是否必须独立部署，再判断业务规则需要怎样组织；微服务解决运行隔离，MVC 与 DDD 解决代码如何放置。

#### 3.5.1 场景一：简单 CRUD 和后台管理——选择组合 A

例如用户后台的“标签管理”，主要是新增、编辑、删除和查询，规则只有名称必填、不能重复等简单校验，也没有多条状态流转。此时采用模块化 MVC 三层即可：handler 接收请求，应用服务完成校验和流程，Repository 读写数据库。

Vibe Coding 可以快速生成这条完整链路，并在同一仓库中完成编译和测试。此时引入完整领域模型和大量 Port，维护成本可能高于收益；拆成独立微服务也没有带来扩缩容或故障隔离价值。

如果整个项目基本都是这类 CRUD，选择组合 A 即可；如果它只是组合 C 中的一个简单模块，也不需要强行设计聚合和领域服务，保持简单的 application 与 domain 即可。

#### 3.5.2 场景二：多个入口必须遵守同一规则——选择组合 C

例如订单可以从用户接口、运营后台、超时任务和消息消费四个入口取消，但都必须遵守“已发货不能取消”“已取消不能重复取消”等规则。如果每个入口都在应用服务中各写一遍判断，AI 新增第五个入口时很容易复制旧代码、漏掉某条规则。

如果这些入口能够稳定复用同一个应用服务，组合 A 仍然够用；当状态规则持续增加，入口开始各自修改订单状态时，更适合模块化单体 DDD：由订单上下文拥有 `Order` 模型，把状态变更收口到 `Order.Cancel()`；application 只负责组织流程，infra 负责数据库和消息。AI 接到“新增取消入口”的任务时，可以沿用同一个领域方法，而不是重新生成一套判断。

同样，当用户上下文中的“用户”表示登录账号，而 CRM 团队口中的“用户”其实是签约客户时，也应让两个上下文维护各自的模型，通过公开契约转换语义，避免 AI 把同一个词直接映射成同一种对象。

#### 3.5.3 场景三：确实需要独立运行——选择组合 B

例如 CMS 的图片处理持续占用大量 CPU，流量高峰与主业务不同，处理失败也不应拖垮内容发布。这里有明确的独立扩缩容和故障隔离需求，适合把图片处理拆成独立服务。

选择微服务的原因是运行需求，而不是代码目录太大。拆分后要为接口契约、客户端版本、集成测试和发布顺序负责；如果图片服务内部也有复杂规则，仍可以在服务内部使用 DDD。部署方式与代码组织方式并不冲突。

#### 3.5.4 场景四：服务经常一起修改和发布——先调整拆分粒度

例如“用户开通主播资格→初始化资产账户→发送 IM 通知→创建直播间”几乎每次变化都要修改四个仓库，而且这些服务没有明显不同的流量、故障隔离或发布节奏。此时问题不是工作空间能否同时打开四个仓库，而是一次需求仍要分别完成契约升级、合并、验证和发布。这通常说明服务拆得过细。

可以先合并为一个部署单元：如果整体仍是纯 CRUD，使用组合 A；如果各模块有自己的术语、状态或少量规则，使用组合 C。反过来，DDD 的限界上下文也不能按功能菜单无限细分；login、register、profile 如果共享同一套模型和生命周期，就没有必要分别建成三个上下文。

#### 3.5.5 新项目选择模块化单体 DDD 的依据

把组合 C 作为新项目的起点，需要同时满足三个前提：

- 项目包含用户、资产、IM 消息、直播等多个业务模块，而不是单一 CRUD。
- 每个模块都有自己的术语、状态或少量规则，但业务逻辑相对轻量，不需要上齐完整的 DDD 战术模式。
- 这些模块暂时没有独立扩缩容、故障隔离或单独发布的需求。

在这些前提下，三个组合都能实现功能，但成本不同。组合 A 上手更快，模型归属和跨模块调用需要团队持续维护；组合 B 提供运行隔离，却提前增加仓库、契约和发布成本；组合 C 保留一个部署单元，同时用限界上下文、领域模型和公开接口明确各模块的职责。

对 Vibe Coding 来说，这种结构还有四项直接价值：

- 目录和业务术语帮助 AI 判断代码应该放在哪个模块。
- 领域方法为状态变更提供固定入口，避免新增入口时重新生成规则。
- Port 和 infra 把数据库、RPC 与消息处理留在适配代码中。
- 同一需求可以集中审阅，四层职责、类型、测试和依赖检查提供固定检查项。

这里采用的是轻量 DDD。简单模块可以只有较薄的 application 和 domain，不必强行引入聚合、领域事件和 CQRS；重点是先确定模型归属、规则入口和跨模块接口。以后某个模块出现独立运行需求时，可以再将它拆成服务，但仍需处理网络延迟、重试、幂等和数据一致性。

**选择结论**：

- 整个项目以简单 CRUD 为主，选择组合 A。
- 项目包含多个轻量业务模块，且暂时统一部署，优先选择组合 C。
- 某个模块确有独立运行需求，将它拆成服务；服务内部仍可使用 DDD。
- 多个服务长期一起修改和发布，应重新评估服务粒度，而不是继续增加服务数量。

**第 3 章结论**：对于多个业务模块组成的新项目，组合 C 通常是更平衡的起点：它保留一个部署单元的开发与发布效率，又用模型、接口和依赖方向约束 Vibe Coding 的生成。组合 A 适合纯 CRUD，组合 B 适合已有明确运行隔离需求的模块；两者是条件明确时的选择，而不是新项目默认拆分的方向。

## 4. 实战代码对比：AI 的复制本能 vs 分层约束

抽象对比容易流于口号，这里用一个反复出现的真实场景把差异摆到代码层面：领域需要"根据一批 UID 查询用户资料"，对方接口暂时只支持单 UID 查询。之后需求演进两次——先要求另一个入口保留封禁用户并标记状态而非直接过滤，再要求所有调用方切到对方新上线的批量接口。

### 4.1 无边界版本：AI 的最快路径是复制

第一次对话交付的实现，把循环调用、协议转换与业务过滤全写在同一个方法里：

```
func (s *UserService) GetProfiles(ctx context.Context, uids []int64) ([]*Profile, error) {
    var result []*Profile
    for _, uid := range uids {
        resp, err := s.client.GetUser(ctx, &pb.GetUserReq{Uid: uid})
        if err != nil {
            continue
        }
        if resp.Status == pb.UserStatus_BANNED {
            continue
        }
        result = append(result, &Profile{UID: resp.Uid, Nickname: resp.Nickname})
    }
    return result, nil
}
```

功能验证通过。当后台管理入口提出"要看到封禁用户并标记状态"时，对话里最快的路径是复制一份变体：

```
func (s *UserService) GetProfilesForAdmin(ctx context.Context, uids []int64) ([]*ProfileWithStatus, error) {
    var result []*ProfileWithStatus
    for _, uid := range uids {
        resp, err := s.client.GetUser(ctx, &pb.GetUserReq{Uid: uid})
        if err != nil {
            continue
        }
        result = append(result, &ProfileWithStatus{
            UID: resp.Uid, Nickname: resp.Nickname, Banned: resp.Status == pb.UserStatus_BANNED,
        })
    }
    return result, nil
}
```

复制变体不是 AI 犯错，而是它在无结构代码库里的理性选择——对话上下文里没有"这段逻辑已存在于别处、应该复用"的信号，复制就是局部最优。真正的考验出现在对方接口升级为批量查询时：需要修改的不是一处，而是每一份复制过循环逻辑的地方。PR 里会出现大量结构相似又不完全相同的改动，审查者要逐一确认每处是否都改对。漏改一处，通常要等到那一处的调用路径出问题才会暴露。

### 4.2 分层版本：契约稳定，改动落点唯一

领域只声明意图，不关心对方一次能查几个：

```
// domain/user/port.go
type ProfileFetcher interface {
    FindByUIDs(ctx context.Context, uids []int64) ([]*Profile, error)
}

// domain/user/service.go
func (s *Service) GetProfiles(ctx context.Context, uids []int64) ([]*Profile, error) {
    profiles, err := s.fetcher.FindByUIDs(ctx, uids)
    if err != nil {
        return nil, err
    }
    return filterBanned(profiles), nil
}
```

对方只支持单 UID 时，循环与协议转换是基础设施的事：

```
// infra/profile_fetcher.go
func (f *profileFetcher) FindByUIDs(ctx context.Context, uids []int64) ([]*user.Profile, error) {
    var result []*user.Profile
    for _, uid := range uids {
        resp, err := f.client.GetUser(ctx, &pb.GetUserReq{Uid: uid})
        if err != nil {
            continue
        }
        result = append(result, toProfile(resp))
    }
    return result, nil
}
```

两次需求演进各自的落点：后台入口要看到封禁状态而非过滤时，改动落在领域层——新增一个不做过滤的用例，或给过滤规则加参数，`FindByUIDs` 与 infra 实现都不动；对方升级为批量接口时，改动只落在 infra 这一个函数体——把循环换成一次批量调用，Port 签名不变，领域层与所有用例零改动。PR 里出现的是一个文件、一个函数体的变更，审查者只需确认新的批量调用语义与循环版本等价。

### 4.3 差异总结

| 维度 | 无边界版本 | 分层版本 |
|------|-----------|---------|
| 第一次实现 | 所有逻辑堆在一个方法里 | 按 Port→infra→domain 分层 |
| 新增变体 | 复制整段代码修改 | 新增用例，复用 Port |
| 外部接口变更 | 每份复制都要改，漏改风险高 | 只改 infra 一处实现 |
| PR 审查 | 多份相似代码逐一核对 | 一个文件、一个函数体变更 |
| 编译护栏 | 无 | Port 未实现、字段未同步 → 本地构建失败 |

需要说明，"外部变化只改一处"本身是 Port 隔离的通用收益，对人工编码同样成立（完整论证见《DDD 的核心优势》第 3 章）。**Vibe Coding 语境下的增量在于**：无结构时 AI 更容易在当前改动点复制一个局部变体，复制件数量可能随会话次数增长，每次变更的漏改风险也随之放大；分层契约则让 `FindByUIDs` 成为可发现、可复用的现成能力，使复用比重新编写循环更自然。**约束改变的不是 AI 的能力，而是它的默认路径。**

## 5. Vibe Coding 的六个困境，DDD 分别怎么兜住

DDD 在 AI 时代的核心价值，是把原先靠人把控的隐性规则，变成模型可理解、结构可强制的显性约束。下面逐条对应——不是"DDD 有什么优势"，而是"Vibe Coding 在这里出了什么问题，DDD 的什么能力正好能兜住"。其中一条常被低估、却最直接对应"糊在一起"问题的能力是：**DDD 天然把功能原子化。**

### 5.1 困境：大需求被 AI 当成一整块任务 → 能力：需求分解

你让 AI 实现“用户开通主播资格后，要初始化资产账户、发送 IM 通知并创建直播间”——它很可能在一个会话里把整条链路全写了：用户规则、资产变更、IM 消息和直播逻辑全部嵌套在同一个文件里，后面任何一个环节要改，都要先理解整段逻辑。**问题不是 AI 不会拆，而是你没有给它拆的框架。**

    L --> L1["Port → infra → domain → interfaces"]
    style U fill:#E3F2FD,color:#000
    style A fill:#E3F2FD,color:#000
    style IM fill:#E3F2FD,color:#000
    style L fill:#E3F2FD,color:#000
```

先按业务语义把大需求拆到不同上下文，再在每个上下文内部按层拆：先定 Port（意图），再补 domain 规则，再写 infra 适配，最后接口层收尾协议转换。一个大需求由此变成一串可以分批交付、分批审查的小需求——每个原子的 diff 都小到人能真正审完。

### 5.2 困境：概念漂移 → 能力：通用语言

你用自然语言告诉 AI"给用户加一个会员等级字段"。AI 可能把这个"用户"理解成登录账号，在 user 表上加字段；但业务上要的是客户档案的等级。同一个词在不同上下文里有不同含义——人知道，AI 不知道。**问题不是 AI 不懂术语，而是你没有给它一份精确的术语词典。**

传统 DDD 里，通用语言解决产品、开发、测试之间的沟通歧义；在 AI 编码中，它首先是一份给 AI 的业务术语词典。核心术语的定义、所属上下文与使用规则一旦稳定，自然语言与代码之间就多了一层语义层："订单履约"不应被实现成"订单支付"，"客户档案"不应去改动登录账号字段。

具体落地时，可以在项目根目录维护一份 `glossary.md`，每条术语记录：名称、所属上下文、精确定义、禁止的用法。例如：

| 术语 | 上下文 | 定义 | 禁止用法 |
|------|--------|------|---------|
| 用户 | membership | 已注册的登录账号，有 UID | 用 User 表示客户档案 |
| 客户 | crm | 签约企业客户，有 customer_id | 用 Customer 表示登录账号 |

这份词典既是给团队看的，也是给 AI 的 system prompt 输入。AI 生成代码前注入术语约束，能显著降低概念漂移的概率。Eric Evans 在 Explore DDD 2024 也鼓励 DDD 实践者实验大模型，并指出：按限界上下文与通用语言加以约束或训练的模型，更接近有用的领域能力 [2]。

### 5.3 困境：可用上下文缺少边界 → 能力：限界上下文

Vibe Coding 的风险之一，是可用上下文没有明确表达模块边界——为完成当前指令，AI 可能跨模块访问内部数据。限界上下文把归属说清楚：每个目录与模块属于哪个业务域、拥有哪些核心模型；跨上下文交互走公开接口或防腐层，而不是直接操作内部对象。与微服务的物理边界不同，限界上下文是逻辑边界，单体与中仓同样可以靠 `domain/<name>` 一类目录划清。

人工开发时，上下文边界常靠资深工程师脑中的地图维持——他知道哪些模块能碰、哪些不能碰。**AI 不会天然拥有这张地图；项目指令可以说明边界，目录结构与接口契约则能把边界稳定地落实到代码中。** `domain/<name>` 既是给人看的边界，也是提供给 AI 的生成范围；防腐层既是解耦手段，也是项目规定的跨域通道。

没有河道的水流，只会漫成沼泽；有河道，奔涌才不会失控。

### 5.4 困境：改外部接口时连带改乱业务逻辑 → 能力：适配隔离

对方接口升级了，你需要改调用方。在无边界的代码里，循环调对方、协议转换、业务过滤全写在一起，改接口意味着同时改三件事——改完之后，业务逻辑有没有被顺手改歪，没人知道。**问题不是 AI 改不对接口，而是业务逻辑和接口适配缠在一起，AI 分不清边界。**

领域只表达意图，外部系统的能力形状留在基础设施——这是 Ports & Adapters 与防腐层的老道理，第 4 章的代码对比就是它最完整的演示。Vibe Coding 语境下的增量在于：**对 AI 而言，稳定的 Port 可以降低外部变化牵动业务逻辑的风险。** 当领域契约不变、实现细节集中在 infra 时，接口适配就有了明确的修改落点，也减少了生成过程顺手改动业务规则的机会。约束再一次改变了 AI 的默认路径：外部接口变化优先落在 infra，而不是扩散到领域层。

### 5.5 困境：AI 可能直接改字段，绕过校验 → 能力：充血模型与聚合入口

你让 AI"把这个订单取消掉"，它可能直接写一行 `order.Status = "cancelled"`——不管订单是不是已经发货。**如果可用上下文和代码结构都没有表达"已发货订单不能直接取消"这条规则，可公开修改的字段就是最直接的实现路径；把规则收进聚合入口，才能让错误路径更难写、也更容易被测试发现。**

以前很多开发者觉得充血模型"麻烦"——为每个状态变更写一个方法，不如直接 `order.Status = "cancelled"` 来得快。这个感受是真实的：人工编码时，充血模型确实增加了击键次数。但在 AI 编码的语境下，**以前觉得"麻烦"的东西，现在变成了"约束"**。

`order.Status = "cancelled"` 是一个没有约束的操作：任何地方、任何时候、任何 AI 都可以写这行代码。而 `order.Cancel()` 是一个收口的入口——AI 必须找到这个方法、理解它的签名、遵守它的前置校验。它不能绕过。这听起来像是"限制了 AI 的自由"，但正是这种限制让生成结果变得可预测、可审查、可信任。

例如，不要这样写：

```
// 贫血：任何地方都可以直接修改
order.Status = "cancelled"
order.UpdatedAt = time.Now()
```

而是把状态变更收口在实体方法里：

```
func (o *Order) Cancel(ctx context.Context) error {
    if o.Status == "shipped" {
        return ErrAlreadyShipped
    }
    o.Status = "cancelled"
    o.UpdatedAt = time.Now()
    o.Events = append(o.Events, OrderCancelled{OrderID: o.ID})
    return nil
}
```

AI 生成代码时，如果只有 `Order.Cancel()` 这一个入口可以改变订单状态，它就不会在别处再写一遍"判断已发货"的逻辑。全项目上齐战术模式并无必要；真正吃紧的是核心域里那少数必须守住的规则——规则只存在于一处时，演进才不会变成多点齐改的赌博。

### 5.6 困境：一次生成的 diff 大到审不过来 → 能力：分层审阅与编译护栏

"整功能一次生成"容易把业务、适配与协议转换嵌套在同一处，审查面对巨大 diff 只能抽查。四层把变更拆成可分面的原子之后，人工审阅有了固定角度：

- domain 是否出现 gorm / proto / 缓存客户端一类框架依赖
- infra 是否塞进业务判定
- interfaces 是否只做协议转换而不写业务

对 AI 而言，按 Port → infra → domain → interfaces 分面推进，单次 diff 可控。再叠加编译层面的约束：Port 未实现、领域误引框架、新增字段未在 infra model / domain entity / 转换函数之间同步——失败可以停在本地构建，而不必拖到联调。

**边界不能保证生成结果业务正确；边界能保证错误更局部、更可见、更可审。**

## 6. 轻量落地：Vibe Coding 需要多少约束

### 6.1 什么情况下需要给 Vibe Coding 加结构护栏

对 DDD 的抵触，常来自"重、慢、前期投入大"的刻板印象。Vibe Coding 语境下，这个问题应该换一种问法：不是"要不要推行 DDD"，而是"AI 的生成行为需要多少最低限度的护栏"。真正吃紧的是战略设计与四层责任面：边界、术语、核心规则，以及"领域不绑框架、适配停在 infra、协议层不写业务"——而不是第一天就上齐事件风暴与全套战术模式。

**需要加护栏的迹象：**

- 业务规则在多个地方以轻微变体重复出现
- AI 生成多次后，同一概念的字段与命名发生漂移
- 一次小改动牵出大面积 diff，审查难以建立"改动↔意图"对应关系
- 编译层面无法拦截跨层漏改

**可以继续使用三层架构的场景：**

- 薄网关或纯编排 HTTP API，几乎没有领域状态
- 没有复杂不变式的简单 CRUD
- 一次性项目或生命周期极短的原型

> 通用的落地清单——最低可行的 DDD 约束、常见反模式、从现有项目的迁移路径——与 AI 语境无关，已移至姊妹篇《DDD 的核心优势》第 6 章，本文不再重复。

### 6.2 一个具体的演进案例：内容管理系统（CMS）——Vibe Coding 视角

抽象的原则需要放到具体场景里才看得清。这里用一个常见的内容管理系统来说明，**当 Vibe Coding 成为主要生产方式时**，架构如何一步步演进。

#### 阶段一：简单 CRUD，AI 随便写

最早期，CMS 就是一个接口：创建内容、读取内容、更新内容、发布内容。数据库一张表，代码三层架构。

**Vibe Coding 在这里的表现：** AI 写 CRUD 几乎不会出错。增删改查逻辑简单、没有复杂状态、没有跨模块依赖。你让 AI 加一个字段、改一个查询条件，它一次搞定，不需要什么架构约束。

```
flowchart LR
    subgraph "阶段一：简单 CRUD"
        API["HTTP API"] --> Service["ContentService<br/>增删改查全在这里"]
        Service --> DB[("content 表")]
    end
```

**这个阶段不需要 DDD。** 做 CRUD 就够，拆 bounded context 反而增加不必要的认知负担。Vibe Coding 在这里是最佳实践——写得快、改得动、审得过。

#### 阶段二：读写分化——没有约束时 AI 开始"糊"

内容量增长后，读场景变复杂：前端列表 + 分页 + 搜索，移动端摘要 + 封面图，SEO 结构化输出。写场景还是增删改。

**Vibe Coding 在这里开始出问题：** 你让 AI 加一个"阅读量统计"的功能，它可能顺手在 ContentService 里加一个字段、在查询方法里加一个 JOIN、在写方法里加一行 `count++`。下一次你让 AI 改发布逻辑，它又可能顺手动到查询方法。"糊在一起"的代码让 AI 无法区分"这是读逻辑"还是"这是写逻辑"——因为代码里就没有这个区分。

**DDD 分层的价值出现：** domain 层只关心写的业务规则（"发布前必须审核""定时发布"），读模型走独立的 query service。AI 生成读代码时，看到的是独立的 QueryService，不会碰 domain 的写规则；生成写代码时，domain 的实体和 Port 告诉它"业务规则在这里，不要绕过去"。

```
flowchart LR
    subgraph "阶段二：CQRS 分层（同库）"
        WriteAPI["写 API"] --> AppService["application<br/>用例编排"]
        AppService --> Domain["domain<br/>内容实体 / 发布规则 / Port"]
        Domain --> WriteRepo["infra<br/>写仓储（MySQL）"]

        ReadAPI["读 API"] --> QueryService["infra / application<br/>读模型 Query Service"]
        QueryService --> ReadDB[("同库，读优化")]
    end
    style Domain fill:#FFCCBC,color:#000
```

注意这里**没有拆服务、没有换数据库**，只是给 AI 的生成范围划了条线——"写逻辑在 domain 里，读逻辑在 query service 里"。AI 每次生成时，上下文是明确的一块，不会乱窜。

#### 阶段三：业务复杂化——AI 需要边界来约束自己

内容管理开始分化：文章管理、多媒体资源、用户权限、发布工作流——各自有独立的规则和生命周期。同一个 `Content` 实体开始承载过多含义。

**Vibe Coding 在这里的典型问题：** 你让 AI"给文章加一个定时发布功能"，它可能顺手在 Content 实体里加了 publishing 的逻辑，又在 media 模块里加了"定时发布时自动生成缩略图"的代码。一次需求改动，牵出三个不相关模块的变更，diff 大到审不过来。

**限界上下文的价值：** 按业务语义拆分后，可以把 AI 的主要生成范围限定在单一上下文内。修改 publishing 时，任务所需的实体与 Port 集中在 `domain/publishing/`，通常不需要触碰 article 和 media 的内部实现。

```
flowchart TB
    subgraph "阶段三：中仓 DDD——AI 的边界围栏"
        direction TB
        Root["CMS 项目根目录"]
        Root --> Domain["domain/"]
        Domain --> A["article/<br/>实体 / 规则 / Port"]
        Domain --> M["media/<br/>实体 / 规则 / Port"]
        Domain --> P["publishing/<br/>实体 / 规则 / Port"]
        Root --> Infra["infra/"]
        Infra --> IA["article/ infra 实现"]
        Infra --> IM["media/ infra 实现"]
        Infra --> IP["publishing/ infra 实现"]
        Root --> App["application/"]
        Root --> IF["interfaces/"]
    end
    style Domain fill:#FFCCBC,color:#000
    style Infra fill:#C8E6C9,color:#000
```

AI 生成的代码被目录结构引导到正确的上下文里。跨上下文交互走 Port 接口，AI 看到的是接口契约而不是内部实现——它不需要知道 media 怎么处理图片，只需要知道 `media.Port.Resize(ctx, ...)` 这个签名。

#### 阶段四：某上下文需要独立部署——Port 让 AI 知道接口在哪里

如果 `media` 上下文的图片处理成为瓶颈，需要独立扩缩容。

**Vibe Coding 在这里的优势：** 因为阶段三已经通过 Port 隔离了依赖，AI 生成跨服务调用代码时，domain 层的接口不动。AI 看到的是同样的 `media.Port` 接口，只是 infra 层的实现从本地方法调用换成了 gRPC 客户端。它不需要理解"为什么以前是本地调用现在要发网络请求"——它只需要实现同一个接口。

```
flowchart LR
    subgraph "阶段四：独立 media 服务"
        CMS["CMS 主进程"] -->|"media.Port<br/>(接口不变)"| MediaService["media 服务<br/>独立部署"]
        MediaService --> MediaDB[("media 专属数据库")]
        CMS --> CMSDB[("CMS 主数据库")]
    end
    style CMS fill:#E3F2FD,color:#000
    style MediaService fill:#C8E6C9,color:#000
```

从阶段三到阶段四，domain 层不需要改任何代码。AI 生成新功能时看到的 Port 接口签名保持不变，只是 infra 层的实现类变了。**Port 接口本身就是给 AI 的 API 文档——"这是你能调用的能力，这是参数类型，这是返回类型。"**

#### 阶段五（可选）：事件驱动 CQRS

如果写模型和读模型的性能差距进一步拉大，可以在阶段三或四的基础上引入事件驱动的 CQRS。但这已经是高阶模式，许多 CMS 到阶段三就足够用了。Vibe Coding 在阶段三已经能获得主要的边界收益——明确的生成范围降低了跨上下文改动的概率，人工审阅也可以优先聚焦一个上下文内的 diff。

#### 演进原则总结（Vibe Coding 视角）

| 阶段 | Vibe Coding 的表现 | 架构做什么 | DDD 对 AI 的价值 |
|------|-------------------|-----------|----------------|
| 一 | 写得快、改得动、审得过 | 不需要 | 还不需要 |
| 二 | AI 开始把读写逻辑"糊在一起" | 读写路径分离 | 给 AI 划分"写归 domain、读归 query"的边界 |
| 三 | AI 一次需求牵出不相关模块的变更 | 按业务语义拆 bounded context | 目录结构 = AI 导航；跨上下文走 Port 接口 |
| 四 | AI 需要跨服务调用，但接口不能变 | 按需拆独立服务 | Port 接口 = AI 的 API 契约，infra 可替换 |
| 五 | 读性能成为瓶颈（可选） | 事件驱动 CQRS | 扩展点，不常用 |

**核心思想**：Vibe Coding 是主生产方式，DDD 是让 Vibe Coding 可持续的护栏。每个阶段的演进都是因为 Vibe Coding 遇到了新的问题，而不是为了"让架构更 DDD"。

## 7. 边界与人工审阅的关系

前面的论述容易被简化成一句过于乐观的结论："有了 DDD，AI 就能放心大胆地写"。这不是本文的立场。

### 7.1 技术债加速

没有约束时，技术债的累积速度是人工开发的数倍——不只是"迟早会出问题"，而是"写完当天就可能已经改不动"：下一轮对话若换个角度重新生成，很容易把上一轮的实现整段推翻重写，业务规则跟着一起被推翻，却没有人真正确认过新旧两版哪一版才对。

这正如第 1.5 节中盖房子的类比所揭示的：地基没打好的房子，盖到三楼开始裂缝，盖到五楼就不敢再加层了。AI 编码也是同样的道理——每一轮"能跑"的新改动都在抬高下一次改动的复杂度，直到某次修改彻底失控。

### 7.2 黑盒化风险

比累积速度更值得警惕的是黑盒化。一段实现如果完全由 AI 生成、又完全交给 AI 修改，中间没有人真正读过、理解过，代码库会退化成一个没有人真正掌握的黑盒：

- **人不掌握**，是因为没看过
- **AI 也不真正掌握**，因为下一次对话通常不带着上一次的完整心智模型，只带着代码文本本身——它能读懂语法，读不出"这段判断为什么这样写"背后的取舍

### 7.3 边界的作用

DDD 分层与限界上下文能做的，是把黑盒的范围缩小、把审阅的入口固定下来——领域规则收在哪、适配细节收在哪，一目了然；一次变更也只落在少数几个原子上，而不是整个系统。

**边界降低的是审阅的成本，不是审阅的必要性**——它把"审全部"变成"审这一小块"，那一小块仍然需要有人真正看过、理解过、确认过，而不是因为 diff 变小了就默认它是对的。

### 7.4 现阶段的分工

AI 在明确边界内生成实现，人确认边界本身有没有被踩、核心规则有没有被写对。结构给的是"让审阅省力"的条件，不是"审阅可以缺席"的许可——至少在当下这个阶段，人工把关仍然是不可替代的一环。

## 8. 总结与展望

### 8.1 核心结论

| 维度 | 结论 |
|------|------|
| 问题本质 | AI 加速了代码生成，也可能加速技术债累积；缺少可执行约束时，高频生成会放大软规范失守的风险 |
| 架构选择 | 纯 CRUD 使用模块化 MVC；包含多个轻量业务模块的新项目优先采用模块化单体 DDD；有明确运行隔离需求时再拆服务 |
| 落地建议 | 从轻量约束开始：划分限界上下文，只为真实业务规则建立领域模型，通过 Port 隔离外部依赖，不必上齐全部战术模式 |
| 人工角色 | 边界降低审阅成本，但不替代审阅；人工把关仍然不可替代 |
| 核心金句 | Vibe Coding 决定系统能跑多快；清晰的语义边界决定系统能跑多远 |

### 8.2 趋势观察

从 Eric Evans 鼓励 DDD 实践者实验 LLM，到 Martin Fowler 指出结构良好的软件对大模型同样更友好 [1][3]，再到曹偲提出的 Architecture Coding [4]——命名尚未统一，方向一致：做复杂系统的人，几乎都会走到"边界 + 生成"这条路上来。

当写代码不再是门槛，生成功能的成本趋近于零，竞争力从实现能力转向抽象、建模与复杂度管控。编码能力越廉价，建模能力越稀缺；生成速度越快，边界价值越高。
